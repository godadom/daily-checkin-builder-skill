# 站点签到流程分析

## 先建立证据记录

在生成实现前创建生成项目的 `docs/site-analysis.md`。只记录脱敏证据、推导过程和未验证假设，不记录任何真实 Cookie、Token、账号或个人数据。

在文档开头填写：

- 站点名称、入口 URL 和签到页面 URL；
- 用户授权范围；
- 直接请求所声明的账号与正常取证范围，以及任何需要澄清的冲突；
- 材料类型、采集时间和来源；
- 是否允许真实网络验证；
- 已知限制与待确认问题。

## 按证据强度读取材料

优先使用能够直接证明客户端行为的材料，并交叉验证：

1. 正式接口文档或站点公开 API；
2. 浏览器 Network 中完整的请求时序与响应；
3. 已脱敏 HAR；
4. 已脱敏 Copy as cURL；
5. 前端 JavaScript 中的请求构造、状态映射和公开签名逻辑；
6. 已有代码与成功、失败响应样例；
7. 截图或用户文字描述。

不得把单个字符串搜索结果当作已确认接口。不得执行未知 cURL、压缩脚本或第三方代码；先静态解析并列出其行为。

### 解析接口文档

- 记录认证方式、方法、路径、参数类型、响应模型和错误码；
- 区分正式承诺与示例值；
- 检查文档版本是否与浏览器实际请求一致；
- 把未在实测材料中出现的可选字段标为“文档声明，未验证”。

### 解析 HAR 与 Network

- 按时间排序请求，区分页面资源、认证、状态查询、签到、刷新和通知；
- 对每个候选请求记录发起者、重定向链、状态码、内容类型和响应摘要；
- 对比签到前后请求，找出真正产生业务状态变化的调用；
- 追踪 CSRF、nonce、时间戳、签名、请求 ID 等动态值从哪里获得、何时失效；
- 忽略分析无关的广告、埋点和静态资源；
- 确认所有秘密已脱敏后再把摘要写入文档。

### 解析 cURL

- 拆解方法、URL、查询参数、请求头、Cookie 和请求体；
- 判断 JSON、Form、Multipart 或其他编码；
- 删除浏览器自动附加且业务不需要的头；
- 保留服务端实际校验的 Origin、Referer、Content-Type、CSRF 等头；
- 把认证值替换为环境变量接口，不把 cURL 原文写进项目；
- 用响应或 Network 时序验证该请求确实是签到请求。

### 解析前端代码

- 定位请求客户端、路由、状态管理、错误映射和签到按钮处理函数；
- 追踪动态参数的输入、编码、哈希或签名步骤；
- 只复现客户端公开执行且属于正常请求所必需的逻辑；
- 不复制混淆代码中的追踪、指纹或反自动化规避逻辑；
- 对无法解释的常量和远端配置标为待验证。

## 重建最小正常流程

按以下顺序画出请求时序：

1. 建立会话或装载已有认证；
2. 获取必要的 CSRF、nonce 或公开配置；
3. 查询当天签到状态；
4. 在未签到时提交签到请求；
5. 再次查询状态，或用可靠业务字段验证结果；
6. 在认证失效且站点提供正常刷新机制时刷新一次 Token；
7. 输出状态并发送可选通知。

为每个关键请求记录一行证据表：

| 阶段 | 方法与脱敏 URL | 参数/请求头 | 认证用途 | 成功依据 | 证据来源 | 置信度 |
| --- | --- | --- | --- | --- | --- | --- |

同时记录：

- Query、JSON、Form 或 Multipart 的字段与类型；
- 必需头和可删除头；
- Cookie、Access Token、Refresh Token、CSRF 的不同用途；
- Cookie 获取结论：按 [站点专用 Cookie 获取与登录交付](cookie-acquisition.md) 确定 `interactive_login`、`network`、`console` 或 `not_applicable`；记录具体登录/状态请求、必需 Cookie 名称、第一方域名、`HttpOnly` 属性、字符串处理、目标环境变量和过期特征，不记录值；
- 重定向是否改变方法、主机、Cookie 或认证状态；
- 动态值的来源、生命周期和重放限制；
- 请求是否幂等；
- 站点允许的调用频率与 `Retry-After` 行为。

## 建立结果判定

不得只依据 HTTP 200 判定成功。结合业务状态码、稳定响应字段、签到状态查询和积分/余额变化建立映射：

| 状态 | 判定要求 |
| --- | --- |
| `SUCCESS` | 本次请求明确成功，且状态查询或可靠业务字段可佐证 |
| `ALREADY_DONE` | 服务端明确表示当天已签到，或签到前状态已确认完成 |
| `AUTH_EXPIRED` | 401、明确认证错误，或登录页重定向等可靠证据 |
| `ACCESS_DENIED` | 认证有效但账号无权执行该签到操作 |
| `TEMPORARY_ERROR` | 超时、429、可恢复 5xx 或服务端临时错误 |
| `SITE_CHANGED` | 响应结构、字段语义或必要请求流程与已验证证据不符 |
| `CONFIG_ERROR` | 必需环境变量缺失、格式错误或账号配置无法解析 |
| `UNSUPPORTED_SECURITY_CHALLENGE` | 流程要求绕过不应自动化的安全挑战 |

对 403、409 和 HTML 形式的 200 响应单独分析：403 可能是认证、权限或安全挑战；409 可能表示重复签到；200 也可能只是登录页或错误页。没有证据时不要强行归类为成功。

## 选择实现方式

按以下优先级选择最简单且稳定的实现：

1. 使用站点公开或正式 API；
2. 使用浏览器实际调用的稳定 HTTP API；
3. 复现正常客户端公开执行且必要的签名逻辑；
4. 仅在普通 HTTP 无法完成、且不涉及规避安全挑战时使用 Playwright 等浏览器自动化。

说明选择理由、放弃其他方案的证据和维护风险。不得仅因方便默认选择浏览器自动化。

若出现 Turnstile、reCAPTCHA、hCaptcha、WAF 挑战、设备证明、WebAuthn 或短信验证：

- 停止自动提交和重试；
- 若挑战发生在手动账号密码/OTP 登录中，按 [交互登录流程](interactive-login.md) 保持操作者电脑上的同一本地 headed 浏览器 context，让用户在原页面完成；青龙仅接收最终 Cookie，不运行浏览器；
- 人工完成后只按已验证的成功 URL、DOM 或响应判据继续，并从当前 context 读取白名单 Cookie；
- 若挑战发生在无人值守签到中、用户未完成、挑战循环出现或无法安全提供可视会话，记录为 `UNSUPPORTED_SECURITY_CHALLENGE` 或登录状态 `LOGIN_UI_UNAVAILABLE`；
- 不得自动求解验证码、调用打码服务、提取挑战 Token、轮换代理或指纹、隐藏自动化、规避检测或重放挑战结果。

## 管理不确定性

把每个结论标为“已验证”“材料支持”或“假设”。为假设写出验证所需的最小材料，不得用猜测填充实现。

在实现前至少确认：

- 签到请求及其前置状态查询；
- 认证和 CSRF 的来源；
- 成功、已签到和认证过期的判定；
- 是否允许安全重试；
- 纯 HTTP 或浏览器方案的选择；
- 尚未验证但会影响正确性的风险。

若认证依赖 Cookie，还必须先完成生成项目的 `docs/cookie-setup.md`。该文档必须基于当前站点证据写出唯一可执行方案；不能只链接本 Skill 的通用参考。若选择交互登录，记录二维码/设备授权生成接口、轮询状态、成功响应、`Set-Cookie` 白名单、超时和平台保存方式；若选择 Network 或 Console，记录精确请求或精确同源表达式、脱敏输出形状及目标环境变量。证据不足则阻塞代码生成。
